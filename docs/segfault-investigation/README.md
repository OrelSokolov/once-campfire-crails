# Crystal 1.21.1: resume мёртвой фиберы после рецикла стека → SIGSEGV

Сегфолт-баг, найденный в once-campfire-crails (parity-сьют capybara-tests).
Этот каталог — материалы для репорта в crystal-lang/crystal.

## Статус

**Минимальный автономный repro ещё НЕ получен.** Проверенные синтетики
(`repro.cr`, итерации v1–v3: churn фибер + Channel/select/timeout + GC
давление + HTTP-сервер с обрывающимися клиентами + пул SQLite с WAL)
не крашатся по 4×120 с, тогда как приложение падает за 20–40 с.
Работающий воспроизводитель на сегодня — приложение целиком (см. ниже).

## Приложение-репродюсер (надёжный)

```bash
git clone <crails-repo> && cd once-campfire-crails/capybara-tests
TARGET=crails bin/run -n /LiveTest/
```

Краш (signal 11) в 1–2 прогонах. Сервер поднимается сам (`bin/app`,
сборка `crystal build --release -Dwithout_mt src/app.cr`). Окружение:
Crystal 1.21.1, Linux x86_64, Ubuntu (libsqlite3 3.50-series).

## Механизм (gdb-форензика, ASLR off)

1. Краш — исполнение мусорного rip после `ret` внутри
   `Fiber::swapcontext` (`*0x555555554000+0x72e0a` — pops+ret).
2. Восстановленные из контекста регистры — детерминированный мусор:
   rdi=rbx=0x555555a93f48 (`first_thread+312`, .bss Boehm GC),
   rbp=r15=0x29, r14=1, r12=0.
3. Объект `Fiber`/`Context` жертвы к этому моменту **отсутствует в куче**
   (поиск сохранённого sp по всем writable-регионам — 0 ссылок) → фибера
   мертва и собрана GC, но её resume всё равно состоялся.
4. Её стек уже рециклирован `Fiber::StackPool` и выдан другой фибере
   (на нём кадры новой хозяйки: `PoolStatement#exec`,
   lib/db/src/db/pool_statement.cr:19) — отсюда маскировка под
   «sqlite/DB::Statement#exec».

Вывод: шедулер резюмит мёртвую фиберу (double-enqueue в runnables или
протухший waiter канала/таймера), стек которой уже переиспользован.

## Что исключено bisect'ом приложения (краш остаётся)

- пул соединений sqlite (`max_pool_size=1` и 5/5);
- fair_busy usleep-хендлер (пересборка без него);
- jobs-воркеры (`JOB_CONCURRENCY=0`);
- Action Cable целиком (WS-хендлер → call_next);
- ping-loop кабеля;
- WriteQueue (writer-фибера + замыкания в стек паркованных фибер);
- libc-overflow (`MALLOC_CHECK_=3` молчит), REGEXP-колбэк sqlite.

Т.е. триггер — в базовом HTTP-пути запроса (request fiber + AR/crystal-db
пул + middleware) при churn'е соединений.

## Финальная добивка (2026-10-16, «Добивай»-раунд)

- Python-bp в gdb ЛОМАЕТ воспроизведение (12 чистых прогонов; голый бинарь
  в той же сессии падает в 1-й итерации) — не использовать.
- Полные бинарные дампы при краше сняты: `/tmp/d-{stack,heap1,heap2,bss}.bin`
  (стек-регион жертвы целиком + Boehm-регионы; оффсеты кадров от вершины
  региона стабильны между прогонами: кадр resume на top-0xAA8, жертва
  rsp=top-0xAE18).
- Решающий факт: sp-кандидаты резюмера (top-0xAA40, top-0xA640 и др.,
  вычислены по его save-блоку) НЕ находятся НИ В ОДНОМ writable-регионе
  кучи — как и sp жертвы. Т.е. в момент краша не существует НИ ОДНОГО
  живого Fiber-объекта, указывающего на этот стек: ни жертва, ни резюмер
  не представлены в куче → resume-цепочка идёт через полностью протухшие
  (собранные GC) структуры: scheduler resume получил мусорный Fiber*,
  загруженный из переиспользованной памяти.

## Дальше

1. Autonomный repro: добавить в `repro.cr` недостающий ингредиент
   (кандидаты: crystal-db retry-семантика после ошибок, PageCache-style
   epoch-инвалидация, middleware railties_cr, nodelay accept-loop).
2. Ловля резюмера (метод отработан наполовину): bp на `ret` в
   `swapcontext` (условие rdi в .bss-диапазоне — срабатывает в момент
   краша) + поиск кадра `resume` (scheduler.cr:123, адрес возврата
   0x5555555a66f9) по стекам фибер. Установлено: резюмер живёт В ТОМ ЖЕ
   регионе стека, что и жертва (кадр на top-0xAA8 региона), т.е.
   рециклированный стек принадлежит самому резюмеру, а Context жертвы
   указывает в него же. Осталось сдампить 48 qword по адресу
   region_top-0xAA8 (region_top = ((rsp-0x400000)/0x800000+1)*0x800000+0x400000)
   и символизировать — это даст точный стек резюмера. Горячий bp на входе
   swapcontext НЕ годится (замедляет всё — краш исчезает).
