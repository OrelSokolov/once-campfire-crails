## Проблема

Большинство `app/views/**.html.erb` — «плоские»: теги без отступов, по
одному на строку. Читать и править такие вьюхи тяжело.

Почему так вышло (это НЕ ограничение Rails и НЕ ограничение фреймворка):

1. Rails-референс (`once-campfire/app/views/...`) — с отступами, читаемый.
   Плоскость — артефакт порта, а не наследие Rails.
2. Вьюхи порта выносились из inline `String.build`-билдеров контроллеров,
   которые генерировали плоский HTML (см. `plans/completed/ERB_REFACTORING.md`). Требование
   byte-parity — «шаблон обязан воспроизводить текущий вывод порта
   байт-в-байт (включая переводы строк!)» — заставило воспроизвести в
   исходнике буквально плоские байты: отступ в исходнике ушёл бы в ответ
   как есть.
3. Компилятор шаблонов `lib/erb_cr/src/template_processor.cr` рендерит
   литеральный текст дословно. Единственный трим — Erubi-совместимый:
   съедается один `\n` сразу после код-тега `<% %>`. Никакой минификации
   или whitespace-стриппинга в пайплайне нет вообще (ни в `erb_cr`, ни в
   `action_pack_cr`; gzip-сжатия ответа тоже нет).

Следствие: если просто добавить отступы в текущие `.erb` — тело ответа
вырастет на них. Ничего их не стрипнет.

Текущее состояние (сверено, НЕ однородное):

- **Плоские** (ведущих пробелов нет): все вьюхи, мигрированные по
  `plans/completed/ERB_REFACTORING.md`, кроме одной — `sessions`, `boosts`, `profiles`,
  `accounts`, `bots`, `rooms/{_form,new,edit}`, `users/show`, `joins`,
  `searches`, `messages/{show,edit}`, `welcome`, `first_runs`,
  `custom_styles`, `directs/new`, `session_transfers`,
  `layouts/_body_close` и др. Вывод — плоский.
- **Уже с отступами** (читаемые, вывод содержит отступы):
  `rooms/show/_composer`, `rooms/involvements/{_bell,_browser_settings,
  _system_settings,_install_instructions}` (ChatERB-группа,
  `app/helpers/chat_erb.cr`), `users/sidebars/_direct`,
  `autocompletable_users/show` (единственная из мигрированных — она была
  перенесена с отступами, и её вывод отступы содержит).
- Вне области: `*.json.jbuilder` (отдельный процессор jbuilder_cr,
  отступы там — форматирование кода, не вывода) и `importmap.html`
  (отдаётся как есть, не через erb-процессор).

Цель: исходник вьюх — читаемый, с отступами; тело ответа — байт-в-байт то
же, что сейчас. Дополнительно ужимать ответ ниже текущего (межтеговые
пробелы, gzip) — отдельная задача, в план не входит.

## Решение

**Compile-time dedent в `template_processor.cr`** — опциональный режим:
при компиляции шаблона из литеральных текстовых сегментов срезаются
ведущие пробелы каждой строки — каждая последовательность `\n[ \t]+` в
тексте между тегами заменяется на `\n`. Отступы исходника не попадают в
вывод; рантайм ничего не платит (это этап компиляции).

Свойства:

- **Пробелы в середине строки не трогаются** (в т.ч. хвостовые за тегом
  на той же строке — `</button>      </fieldset>` сохраняется как есть):
  dedent применяется только к пробелам СРАЗУ после `\n`. Этого достаточно
  для 100% воспроизведения текущего плоского вывода.
- **Переводы строк не добавляются и не убираются** — только ведущие
  пробелы строк. Erubi-трим `\n` после `<% %>` сохраняется.
- **Хвостовой `\n` файла** воспроизводится как раньше (см. гоччу про
  `boosts/index.html.erb` в `plans/completed/ERB_REFACTORING.md`).

Почему режим опциональный (а не безусловный): у ChatERB-группы и
`autocompletable_users/show` текущий вывод УЖЕ содержит отступы, и он
зафиксирован в parity-бейзлайнах. Безусловный dedent молча изменил бы эти
ответы. Поэтому:

- `compile_template` / `compile_layout` / `compile_partials` получают
  именованный аргумент `dedent : Bool = false`, прокидываемый в
  `run("./template_processor", path, dedent)`.
- Включается точечно: `action_pack_cr` (`base.cr`, implicit render
  экшен-шаблонов `__av_tpl_*`) и `compile_partials` для `rooms/_form`
  в `rooms_controller.cr`. ChatERB-сайты в `chat_erb.cr` — БЕЗ dedent,
  их вывод не меняется.

Правило переформатирования вьюх (гарантирует byte-parity):

1. Строковая структура сохраняется 1:1 — строки не склеиваются, не
   переносятся (длинные строки остаются длинными). Добавляются ТОЛЬКО
   ведущие отступы строк.
2. Контент `<pre>`/`<textarea>` не переносится на отдельную строку —
   ведущие пробелы внутри них значимы (в текущих вьюхах оба `<textarea>`
   — `profiles/show`, `custom_styles/edit` — уже однострочные, такими и
   остаются).
3. Отступ — 2 пробела на уровень вложенности, по образцу Rails-референса.

Отвергнутая альтернатива: рантайм-минификация (middleware, срезающий
межтеговые пробелы). Дает ответ меньше текущего, но: ломает byte-parity
всех существующих parity-отчётов/capybara-бейзлайнов, требует
нормализации при каждой сверке, ест CPU на каждый ответ, и HTML-whitespace
collapsing небезопасен для inline-элементов (`<a> <a>` — видимый пробел),
`<pre>`, `<textarea>`.

## План

### Этап A — фреймворк (erb_cr), по AGENTS.md

1. Патч в локальном `lib/erb_cr/src/template_processor.cr`: dedent
   литеральных текстовых сегментов (`\n[ \t]+` → `\n`) при переданном
   флаге. Plumbing: `rendering.cr` — `compile_template`/`compile_layout`/
   `compile_partials` принимают `dedent : Bool = false` и передают в
   `run()`. Spec в `lib/erb_cr/spec/`: многострочный сегмент с отступами
   (dedent=true — режет, dedent=false — как было), пробелы после `%>` на
   той же строке не трогаются, `\n` после `<% %>`-тега съедается как
   раньше, хвостовой `\n` файла сохраняется.
2. `action_pack_cr`: `compile_template "__av_tpl_...", path, dedent: true`
   в `base.cr` (implicit render). Тоже локальный шард → та же схема
   публикации (см. п. 3–4), отдельным bump.
3. Проверка «патч сам по себе ничего не меняет»: у целевых (плоских)
   вьюх ведущих пробелов нет, dedent для них — no-op. Сборка
   `tmp/app-before` (до патча) и `tmp/app-after` (после), оба сервера на
   копии БД, `curl` + `cmp` всех HTML-эндпоинтов — нулевая разница.
   Гочча: `autocompletable_users/show` компилится через тот же implicit
   path в `base.cr`, но имеет отступы — если флаг включается ВСЕМ
   implicit-шаблонам, его вывод изменится. Решение: либо перечислить
   исключения в `base.cr`, либо сразу отнести файл к этапу C (см. ниже)
   и сверять его нормализованным diff.
4. `~/myshards/`: найти шарды erb и action_pack, внести те же патчи,
   опубликовать с bump version (erb_cr v0.1.2, action_pack_cr —
   следующий патч).
5. Подтянуть опубликованные шарды в проект (`shard.yml`: версии),
   `shards update`, пересобрать.
6. `rake build:crails` — проверка сборки.
7. Повторить byte-сверку из п. 3 против опубликованных шардов.

### Этап B — переформатирование плоских вьюх

Группами (внутри группы — один коммит, верификация до/после по
процедуре `plans/completed/ERB_REFACTORING.md` «Верификация»: `tmp/app-before`/
`app-after` на копии БД, `curl` + `cmp` побайтово; затронутые эндпоинты —
как в таблице инвентаризации `plans/completed/ERB_REFACTORING.md`):

1. Простые full-page экраны: `welcome`, `first_runs`,
   `session_transfers`, `custom_styles`, `sessions`, `searches`.
2. Формы: `accounts`, `profiles`, `directs/new`, `rooms/{_form,new,edit}`,
   `messages/edit`, `boosts/{index,new}`, `bots/{index,new,edit}`.
3. Остальные экраны: `users/show`, `joins`, `messages/show`,
   `layouts/_body_close`.

Порядок в группе: сначала самый простой файл, сверка, потом остальные.
Критерий на каждом шаге — нулевая побайтовая разница вывода.

### Этап C — нормализация уже-читаемых вьюх (опционально)

Включить dedent для ChatERB-группы (`chat_erb.cr`) и, если не сделано
исключением в этапе A, для `autocompletable_users/show`: исходники уже
читаемые и не меняются, но вывод теряет ведущие пробелы строк — тело
ответа уменьшается. Верификация — нормализованный diff
(`diff <(sed 's/^[ \t]*//' old) <(sed 's/^[ \t]*//' new)`) + capybara;
parity-бейзлайны этих эндпоинтов перезаписываются. Отдельный коммит,
можно отложить/пропустить — на читаемость исходников не влияет.

### Этап D — финал

1. Полный прогон parity (`tmp/parity_report.py`) + capybara-набор —
   зелёные без перебазлайна (вывод не менялся; исключение — этап C,
   если делался).
2. Обновить `plans/completed/ERB_REFACTORING.md` п.5 (byte-parity теперь гарантируется
   dedent-режимом компилятора, а не отсутствием отступов в исходнике) и
   этот файл — статус «завершено».

## Верификация каждого шага (обязательна)

Как в `plans/completed/ERB_REFACTORING.md`: сборка до/после (`crystal build src/app.cr
-o tmp/app-{before,after} -Dwithout_mt`), серверы на тестовой копии БД,
`curl` всех задетых эндпоинтов до/после → `diff`/`cmp` побайтово.
Критерий: нулевая разница на каждом шаге этапов A–B (для этапа C —
нулевая разница после нормализации ведущих пробелов).
